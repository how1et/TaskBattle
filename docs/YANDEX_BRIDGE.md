# Переход со старого адреса TaskBattle

Переходный прокси сохраняет старый адрес в браузере и пересылает запросы в один заранее настроенный сервер Yandex. Это позволяет использовать прежние ссылки, `sessionStorage`, IndexedDB и локальные черновики. Часть ссылки после `#` остаётся в браузере. Перенаправление всего сайта на другой домен этих свойств не сохраняет.

Реализация подготовлена локально. Публикация и включение требуют отдельной проверки настоящих HTTPS-адресов и сохранённого черновика на старом адресе. Пока это не проверено, перенос рабочего трафика запрещён.

## Конфигурация

| Настройка                 | Старый Sites                                   | Новый сервер Yandex                |
| ------------------------- | ---------------------------------------------- | ---------------------------------- |
| `MIGRATION_TARGET_ORIGIN` | Точный новый HTTPS origin                      | Не задавать                        |
| `MIGRATION_SOURCE_ORIGIN` | Точный старый HTTPS origin                     | Тот же старый HTTPS origin         |
| `MIGRATION_BRIDGE_KEY`    | Отдельный секрет: 64 шестнадцатеричных символа | Тот же секрет из Lockbox           |
| `MIGRATION_SECRET`        | Отдельный ключ служебного переноса             | Отдельный ключ служебного переноса |
| `RUNTIME`                 | Обычный режим Sites                            | `yandex`                           |
| `APP_ORIGIN`              | Не требуется для прокси                        | Точный новый HTTPS origin          |

Origin содержит только протокол и имя сервера, при необходимости порт: без пути, завершающего `/`, параметров, фрагмента или логина. Значения должны быть каноническими: например, `https://new.example.test`. Старый и новый origin должны различаться. Секрет прокси не должен совпадать с ключом миграции; его нельзя передавать клиентскому JavaScript, коммитить или печатать в журнале.

Пустой `MIGRATION_TARGET_ORIGIN` оставляет старое приложение в обычном режиме. Непустое некорректное значение закрывает доступ с ошибкой; оно не включает запасную запись в D1. После переключения запрещено убирать эту настройку или публиковать на Sites старую версию без прокси: такой откат снова открыл бы устаревшую базу.

## Точка входа и границы доверия

В сборке Sites `vite.config.ts` использует `worker.ts`, который вызывает `handleBridge` перед действующим `vinext/server/fetch-handler`. ASSETS подключён с `run_worker_first: true`, поэтому и страницы, и API, и файлы нового интерфейса сначала проходят через прокси. Сборка Yandex сохраняет отдельную существующую точку входа.

Адрес назначения берётся только из конфигурации. Путь и параметры копируются без возможности выбрать другой сервер. Прокси проверяет исходные `Origin` и `Sec-Fetch-Site` до замены origin. Разрешено открыть страницу по внешней ссылке из мессенджера; это исключение не разрешает обращения к API с другого сайта.

Старый Worker берёт IP из `cf-connecting-ip`, заменяет любые входящие заголовки моста и передаёт `x-taskbattle-bridge-key`, `x-taskbattle-bridge-source`, `x-taskbattle-bridge-client-ip`. Новый API принимает этот IP только после `verifiedBridgeClientIp`: проверяет отдельный ключ, точный source origin и формат адреса. Caddy продолжает формировать свой `x-taskbattle-client-ip` для прямых запросов; он не должен стирать три заголовка моста до серверной проверки. Ошибочный или неполный набор заголовков моста получает отказ, а не обход проверки. Сетевой доступ к Node допускается только через настроенный Caddy.

Прокси пересылает текущие `x-attempt-key` и `x-teacher-key`, потоки фотографий и заголовки навигации Vinext. Cookie, Authorization, Referer, произвольные forwarded-заголовки, ключи миграции и очистки не уходят на новый сервер. Ответы API и страницы не кэшируются. Cookie и служебные заголовки нового сервера клиенту не выдаются. Перенаправления допускаются только внутри нового origin и переписываются на старый адрес; внешнее перенаправление возвращает ошибку.

Один запрос имеет предел ожидания 85 секунд, короче 90-секундного ожидания экспорта в интерфейсе. Прокси никогда автоматически не повторяет POST: новый сервер мог сохранить ответ до разрыва связи. Повтор со стороны интерфейса использует существующие request ID и серверную идемпотентность.

## Старые файлы интерфейса

Открытая до переноса вкладка может позднее запросить файл своей старой сборки. Если новый сервер вернул 404, ошибку 5xx или недоступен, Worker может отдать этот файл через ASSETS. Разрешены только GET/HEAD для известных расширений внутри `/_next/static/` или `/assets/`. HTML, JSON, source maps, фото пользователей, API и страницы таким способом не обслуживаются. Отсутствующий файл не вызывает старый обработчик приложения.

ASSETS должен содержать файлы сборки, которая уже открыта у пользователей. Обычная новая сборка не гарантирует сохранение этих файлов. Перед публикацией моста необходимо сохранить клиентские файлы текущего опубликованного релиза и включить их в набор статических файлов переходного релиза без замены файлов с тем же именем и другим содержимым. Пока наличие старых файлов не подтверждено, переключение запрещено. Сохранить их следует на весь срок доступности старых вкладок/ссылок.

## Порядок переключения

1. Подготовить новый HTTPS origin, хранилище секретов, ограничения сетевого доступа и новый сервер. Проверить прямой доступ, фотографии, экспорт и резервное восстановление на синтетических данных.
2. Подготовить и проверить прокси на отдельном тестовом старом origin. Проверить обе версии интерфейса: уже открытая вкладка со старым JS и новая загрузка. Проверить старые статические файлы, teacher/attempt-ссылки, локальный черновик и отправку фотографии после краткого обрыва связи. Проверить отказ при подделке Origin, IP и ключа.
3. На исходном сайте включить `MIGRATION_DRAIN=1`. Новые комнаты и попытки не открываются; активные попытки продолжаются. Дождаться `activeAttempts=0`. Просроченные попытки должны закончиться штатным серверным завершением, а не удалением строк.
4. Заморозить исходную базу. Сервер разрешает это только при включённом drain и атомарном отсутствии незавершённых попыток. Снять и проверить полный снимок таблиц и обязательных фотографий, импортировать с исходными ID и датами. Новая база после импорта остаётся замороженной.
5. Сверить снимок, фото и целостность новой базы. Включить подготовленный мост на старом origin. Служебные `/api/migration/*` остаются локальными и сохраняют свою авторизацию; `/api/migration/status` показывает исходную базу. `/api/migration/unfreeze` на старом origin отклоняется, включая варианты с повторными и завершающими слешами.
6. Проверить, что обычные обращения со старого origin идут в новый сервер, исходная база всё ещё заморожена и при недоступности Yandex API получает ошибку. Только после этого отдельно снять заморозку и drain на новом сервере. Повторно проверить сквозной путь из старой вкладки с черновиком и фото. Не объявлять завершение переноса по одним локальным тестам.

Попытки, уже начатые до drain, не прерываются переносом: их нужно завершить до заморозки. Черновик комнаты без начатой попытки может оставаться только в старом браузере — именно для него нужен проверенный мост, сохранённые файлы и прежний origin. Закрытие вкладки или очистка данных браузера не являются способом переноса черновика.

## Откат и срок работы

После первой записи в Yandex откат выполняется совместимой предыдущей версией приложения поверх той же актуальной базы Yandex и того же хранилища фотографий. Размораживать исходную D1 нельзя: новые ответы и комнаты там отсутствуют. Восстановление резервной копии с потерей более новых записей требует отдельного согласованного решения; это не автоматический аварийный режим прокси.

Пока старые адреса обслуживает мост, Cloudflare/Sites остаётся участником передачи трафика. Это переходный режим, а не полное исключение иностранной инфраструктуры. Новые ссылки можно создавать на новом домене; прекращение поддержки старого origin возможно только после отдельно согласованной политики для действующих ссылок и локальных черновиков.

Локальные регрессионные проверки находятся в `tests/bridge.test.mjs`. Они проверяют потоковую передачу тела, доверенный IP, закреплённый upstream, запрет повторного POST и отката на старый API, перенаправления, локальные служебные маршруты и ограниченный запасной путь для статических файлов. Это не заменяет испытание опубликованного моста и реальной сохранённой вкладки.
