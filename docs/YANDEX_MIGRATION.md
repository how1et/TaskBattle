# Перенос TaskBattle: состояние и порядок переключения

Ветка `codex/yandex-migration` готовит существующее приложение к Node.js 24, SQLite и закрытому Yandex Object Storage. Рабочий Sites-сайт не переключён. Биллинг, собственный домен/DNS и OAuth Диска ещё должны быть подключены; реальные пользовательские данные не экспортировались.

## Запуск для локальной проверки

```sh
npm ci
npm run build:yandex
npm run dev:yandex
# в другом терминале
TEST_URL=http://127.0.0.1:3000 npm run test:integration
```

На Windows: `$env:TEST_URL='http://127.0.0.1:3000'`. Открыть http://127.0.0.1:3000. SQLite и тестовые фотографии сохраняются в игнорируемом `var/local-yandex`. Это файловая имитация Object Storage для локального тестирования; производственный `runtime/start.mjs` всегда подключает Яндекс. До подключения Диска экспорт показывает понятное сообщение.

SQLite требует Node 24 с исправленной SQLite (3.51.3+ или соответствующий поддержанный backport, проверяется при запуске). Используются один процесс приложения, WAL, FULL synchronous, foreign keys, busy timeout и атомарные batch. Не запускать несколько VM поверх одной SQLite или копировать только `.sqlite` при активном WAL.

## Инвентарь

Переносятся `rooms`, `tasks`, `attempts`, `answers`, `attempt_intervals`, `attempt_operations`, `sheet_exports`, `blobs`, `expired_attempts`, `rate_limits`, `cancelled_answers`, а также все фотографии, на которые ссылаются `tasks.file_key` и `answers.solution_key`. Идентификаторы, хеши доступа и даты копируются без пересчёта. Сроки остаются 14 дней / 24 часа / 72 часа. Google-файлы не читаются и не удаляются.

SQL `0006_migration_gate.sql` добавляет блокировку записей и административный шлюз. `0007_yandex_exports.sql` добавляет долговечный журнал XLSX. Это ручные SQL-миграции, применяемые по порядку; `runtime/migrate.mjs` сверяет контрольные суммы, схему и целостность. После импорта версии 6 принятие миграций через `--adopt-existing --adopt-through 6` не запускает исторический backfill повторно, затем применяется только 0007. Не запускать `db:generate` для удаления объектов ручных миграций.

## Безопасное окно

1. Сначала подготовить отдельную VM, закрытые бакеты, Lockbox, HTTPS и тестовую базу. Пройти локальные и реальные проверки на синтетических данных, включая фото и Диск. См. [инфраструктуру](YANDEX_INFRA.md) и [экспорт](YANDEX_DISK.md).
2. Согласовать время переключения. На старом сайте применить 0006, задать секрет миграции через серверное хранилище и включить `MIGRATION_DRAIN=1`. Новые комнаты/попытки временно не создаются, существующие продолжаются. Подождать завершения активных попыток (максимум их исходные 24 часа), обработать overdue через обычную очистку. Даты не продлевать.
3. Freeze разрешён только при drain и отсутствии незавершённых попыток; проверка атомарна. Снимать финальный экспорт лишь после freeze. SQL-триггеры запрещают поздние записи. Не проводить перенос активных попыток без отдельного проверенного протокола паузы.
4. `scripts/migration-transfer.mjs` получает снимок через HTTPS и секрет из отдельного файла вне репозитория. Использовать `--help`. Каталог снимка новый и вне Git; каждый файл и JSON-пакет имеет SHA256. Неполный/изменившийся снимок не принимается. Сначала сохранить резервную копию этого снимка в закрытом хранилище.
5. `scripts/restore-migration.mjs` импортирует только в новую базу, сверяет все количества, внешние ключи и байты фотографий. Чужие данные и существующий файл базы не перезаписываются. Импорт остаётся **замороженным**, в том числе при частичной ошибке. Повторять в новом пути после устранения причины; не включать непроверенный импорт.
6. Проверить отчёты/фото/сроки на контрольных объектах, убрать staging maintenance, явно разморозить только новую базу и направить пользователей на неё. Старую D1 не размораживать после появления новых записей в Яндексе.

## Старые ссылки и открытые вкладки — блокер переключения

Адрес `taskbattle.danprosvirin.chatgpt.site` принадлежит Sites; перенести его DNS в Яндекс нельзя. Собственный HTTPS-домен пока не выбран. Для перехода требуется временный проверенный proxy на старом адресе, направляющий API и страницы на новый сервер при сохранении старого origin, IndexedDB и фрагмента `#` ссылки. **Этот переходный proxy ещё не реализован и не проверен; утверждать работоспособность старых ссылок после переноса нельзя.** Простое перенаправление не переносит локальный неотправленный черновик.

Требования к bridge: фиксированный HTTPS destination, проверка исходного Origin до переписывания, отдельный серверный ключ, проверка доверенного IP на получателе, запрет редиректов с credential forwarding, никакого fallback API на старую D1. Старые immutable JS chunks должны остаться доступны; административный status старой базы не проксируется. E2E включает открытую до переключения вкладку с фото-черновиком, lost-response retry, spoofed headers и отказ upstream. До такой проверки cutover запрещён. Cloudflare остаётся временным участником доставки старых ссылок, это нужно честно учитывать.

## Резервирование и откат

`runtime/backup.mjs` делает SQLite online backup, проверяет integrity/FK, переносит доступные зависимости в content-addressed `objects/` (9 дней), затем последним пишет manifest в `snapshots/` (7 дней). База тоже хранится в `objects/`: её срок не короче manifest. При сбое нет ложной готовой копии. До трёх попыток в рамках двухчасового systemd задания. Замена фото во время копирования может вызвать безопасный отказ; проверять ошибки, а не считать ежедневное расписание гарантией восстановления за 24 часа.

`restoreBackup` сверяет все SHA256, запрещает замену существующей базы или отличающегося объекта и публикует целый файл базы атомарно, в замороженном состоянии. Регрессионный тест проверяет реальное восстановление. Проверка в Yandex Object Storage ещё требуется.

Откат до открытия нового сайта: отключить новую площадку, убедиться, что новых записей нет, вернуть старую из drain/freeze. После новых записей: **предыдущая совместимая версия кода на той же актуальной SQLite и бакете**. Возврат DNS к устаревшей D1 потеряет ответы и запрещён. Восстановление старого backup требует отдельного согласования потери/сверки новых записей. Не удалять старый хостинг и его данные до подтверждённого перехода.

## Проверки на этой ветке

Автотесты охватывают прежние сценарии, перенос 11 таблиц и фото, сохранение дат, отказ при повреждённых снимках, SQLite atomicity, XLSX повторы/параллельность/неопределённую загрузку, резервное восстановление. Локальный Node HTTP-сценарий: 25 задач, фото >1 МиБ, double-submit, потеря ответа после commit, отдельная попытка, отчёт и ACL фото. Браузерные проверки и итоговый счёт тестов фиксируются в PR после завершения прогонов. Реальные камеры iOS/Android, Yandex IAM/HTTPS/Object Storage и живой Диск этими тестами не подтверждаются.
